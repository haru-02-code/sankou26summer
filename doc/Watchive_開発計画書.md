# Watchive 開発計画書

## 1. アプリの目的（解決したい問題）

- サブスクサービスのウォッチリストは、そのサービス内の作品しか選べず、全ての映画を対象にしたリストにならない
- 記憶は時間とともに薄れていくため、自分が観た作品の記録を残したい
- 過去に観た映画に自分自身でスコアを付けることで、自分だけの作品ランキングを作りたい

---

## 2. 画面構成

### ① 作品検索画面
- TMDb APIで検索し、ポスター・タイトル・公開年を一覧表示
- ポスターをクリック → 作品詳細画面へ遷移

### ② 作品詳細画面
- レイアウトは現行の `movie_detail.html` をベースに、中身を刷新
- 表示内容：ポスター、背景シーン画像、タイトル、公開年、ジャンル、あらすじ
- 操作：ウォッチリスト追加ボタン、レビュー作成ボタン（モーダルでレビュー作成）
- レビューを書いた作品には、視聴日（必須）・マイスコア（必須）・感想が追加表示され、マイログ画面に反映される

### ③ マイウォッチリスト画面
- 観たい作品の一覧表示
- 作品検索から作品を追加できる

### ④ マイログ画面
- 現行の `index.html` のレイアウトを踏襲
- 自分が視聴済みの作品を一覧表示
- 並び替え機能（登録日順／作品名順／スコア順）
- ジャンル絞り込み機能（要TMDbジャンル対応表）
- ポスタークリックで作品詳細画面へ遷移

## 3. データベース設計（3テーブル構成）

これまでの `movies` 単一テーブルから、役割ごとに3テーブルへ分割する。

### `movies`（作品カタログ／TMDbのキャッシュ）

| カラム | 型 | 内容 |
|---|---|---|
| id | int, PK, auto_increment | 自分のDB内の主キー |
| tmdb_id | int, unique | TMDb側のID（重複登録防止） |
| title | varchar(255) | 作品名 |
| overview | text | あらすじ |
| poster_path | varchar(255) | 自分の `static/uploads/` に保存した画像パス |
| backdrop_path | varchar(255) | 同上（背景シーン画像） |
| release_date | date | 公開年月日 |
| genre_ids | varchar(255) | ジャンルID（カンマ区切り等で保存） |
| created_at | datetime | 初回取得日時 |

### `watchlist`（観たい作品リスト）

| カラム | 型 | 内容 |
|---|---|---|
| id | int, PK, auto_increment | 主キー |
| movie_id | int, FK → movies.id | 対象作品 |
| added_at | datetime | 追加日時 |

### `reviews`（視聴ログ／旧movies相当）

| カラム | 型 | 内容 |
|---|---|---|
| id | int, PK, auto_increment | 主キー |
| movie_id | int, FK → movies.id | 対象作品 |
| watched_date | date | 視聴日（必須） |
| rating | int | マイスコア（必須、100点満点・0.5刻みは要検討） |
| review | text | 感想 |
| created_at / updated_at | datetime | 登録・更新日時 |

**必須要件（INSERT・SELECT）は、この `reviews` テーブルへの操作として引き続き満たす。**

## 4. 画像の取り扱い方針（案B採用）

- TMDbの画像URLをそのまま使うのではなく、**初めて触れた作品の画像は `static/uploads/` にダウンロードして保存する**
- 保存タイミング：検索結果から作品詳細に初めてアクセスした時、または初めてウォッチリスト／レビューに追加された時
- 物理削除のタイミング：`movies` テーブルの当該作品が、`watchlist` にも `reviews` にも一件も紐付かなくなった時にのみ、画像ファイルを削除する
- これにより、既存の加点要素「画像アップロード＋物理削除」の実装方針を活かす

---

## 4.5. 映画／TVシリーズの検索対応

- テーマが「映画・アニメ視聴ログ」であり、ドラマ・TVアニメも扱うため、TMDbの `/search/movie` に加えて `/search/tv` にも対応する
- 実装方式：**タブ切り替え方式（パターンB）を採用**
  - 検索画面に「映画」「TV」のタブを設置
  - 選択中のタブに応じて `/search/movie` または `/search/tv` のどちらかを呼び出す
  - まずはこの方式で実装し、余裕があれば将来的に同時表示（パターンA）へ拡張することも検討
- `/search/tv` はレスポンスのキー名が一部異なる点に注意（`title`→`name`、`release_date`→`first_air_date` 等）。`movies` テーブルに保存する際は、映画・TV共通のカラム名に揃えて格納する

---

## 5. ジャンル絞り込み機能について

- TMDbの `genre_ids` は数値配列のため、人間が読める名称に変換する対応表が必要
- TMDbの `genre/movie/list` エンドポイントからジャンル対応表を取得し、アプリ内に保持する
- マイログ画面の絞り込みプルダウンに反映する

---

## 6. Gmail自動通知の仕様

タイミング：**レビュー投稿時（`reviews` へのINSERT時）**

- 通常のレビュー投稿時：
  「〇〇のレビューを記録しました（スコア: 75点）」
- 高スコア（例：90点以上）または自己ベスト更新時：
  「〇〇に90点をつけました！あなたの歴代トップ作品の1つです」

## 8. 実装ステップ（想定順序）

1. DB設計変更：`movies` / `watchlist` / `reviews` の3テーブルを作成し、`database.sql` を更新
2. TMDbジャンル対応表の取得・保持
3. 作品検索画面（ポスター一覧＋詳細への遷移）
4. 作品詳細画面（TMDbデータの表示、初回アクセス時に `movies` へINSERT、画像ダウンロード処理）
5. ウォッチリスト追加機能
6. レビュー作成（モーダル）→ `reviews` へINSERT、Gmail通知
7. マイログ画面（`reviews` × `movies` のJOIN、並び替え・ジャンル絞り込み）
8. マイウォッチリスト画面
9. 既存デザイン（ダークシネマ、明朝体、レターボックス風背景等）を新画面へ展開
10. オブジェクト指向リファクタリング
11. 提出物準備（概要文、アピール動画、SQLファイル）

## 11. その他の決定事項

- **同一作品への複数レビュー**：許可する（再視聴のたびに別レビューとして記録できる。`reviews`テーブルにユニーク制約は付けない）
- **既存データの移行**：行わない。3テーブル構成への切り替え時に、現行の `movies` テーブルの登録済みデータ（テスト登録分）は削除し、ゼロから登録し直す
- **TMDbクレジット表記**：画面フッター等に "This product uses the TMDB API but is not endorsed or certified by TMDB." を掲載する。提出物の概要文にも明記する
- **モーダル（レビュー作成）の実装**：jQueryを使用する
- **スケジュールが厳しくなった場合の優先順位**：計画書「8. 実装ステップ」に記載の順序をそのまま優先順位として採用する

  2. マイログ画面・作品詳細画面
  3. ウォッチリスト機能
  4. Gmail通知・ジャンル絞り込み
  5. デザインの仕上げ・OOPリファクタリング
